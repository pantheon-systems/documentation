# Signal dimensions

Generated by `node scripts/signals.cjs describe --markdown`. Do not edit by hand; edit `scripts/lib/signals.cjs`.

## User tasks and journeys (`tasks`)

- Assessment: a script gathers and flags; a person or Claude judges
- Input: a signal file named in the profile under `inputs.tasks`
- Minimum evidence: Tasks declared in the profile (evaluate, first success, configure, develop, deploy, operate, troubleshoot, recover, migrate, offboard). Walkthrough results, when supplied here, show where a reader is blocked.
- Provenance needed: who performed the walkthrough; date; environment or version used
- Limitations: Declared tasks are what the team believes readers do, not observed behavior. A walkthrough covers one path by one person. Missing prerequisites, transitions, verification, and next steps are judged by reading, not counted.
- If missing: status "not assessed". Request: Add the tasks readers must accomplish to the profile, then record at least one walkthrough per required first-success task (who, when, which version, where they got blocked).
- Item fields: `task`* (string), `performedBy`* (string), `date`* (date), `result`* (succeeded|partial|blocked), `blockedAt` (string), `environment` (string), `notes` (string) (* required)

## Audience and environment (`audience`)

- Assessment: needs human or Claude judgment
- Input: the profile and the inventory (no signal file)
- Minimum evidence: Audience roles and environments named in the profile. They are candidate axes to check coverage against, not product capabilities.
- Provenance needed: where each audience or environment was named
- Limitations: Do not invent plans, platforms, frameworks, or permissions the product does not have. An axis nobody named is not assessed.
- If missing: status "not assessed". Request: List audiences (for example beginner, experienced, developer, administrator, operator) and supported versions, platforms, and plans in the profile, citing where each comes from.

## Documentation type (`docTypes`)

- Assessment: a script gathers and flags; a person or Claude judges
- Input: the profile and the inventory (no signal file)
- Minimum evidence: Published pages in the evidence scope. The script suggests a type per page and section from structure; a person confirms by reader need.
- Provenance needed: the page inventory run
- Limitations: Structure cues are not reader need. A reference mention does not show a task is documented. Not every feature needs all four types. Mixed pages are flagged, not forced into one type.
- If missing: status "not assessed". Request: Run the inventory stage so pages exist to classify.

## Demand (`demand`)

- Assessment: a script gathers and flags; a person or Claude judges
- Input: a signal file named in the profile under `inputs.demand`
- Minimum evidence: An approved export of repeated reader questions (support, Jira, community, onboarding, sales or customer-success objections, example requests) with a time window and a note on how the sample was chosen.
- Provenance needed: source system; retrievedAt; approval; timeWindow; sampling method; whether the sample is biased
- Limitations: Message counts are not user counts. Report frequency, unique threads, and unique requesters separately; requesters stay unknown unless the source says. Tagged or surfaced samples are biased. Silence is not evidence of no need.
- If missing: status "not assessed". Request: Export support threads, Jira issues, community questions, or onboarding notes for this area for a stated time window, with approval to use them, and stage them as the demand input.
- Item fields: `id`* (string), `sourceType`* (support|jira|community|onboarding|sales|cs|other), `task` (string), `terms` (array), `date`* (date), `threadId` (string), `requesterIds` (array), `requesterCount` (number), `impact` (string), `exampleRequest` (boolean), `excerpt` (string) (* required)

## Search and discoverability (`search`)

- Assessment: a script gathers and flags; a person or Claude judges
- Input: a signal file named in the profile under `inputs.search`
- Minimum evidence: An approved export of internal search queries or no-result searches, with a time window. Navigation, links, titles, and competing pages come from the inventory.
- Provenance needed: source system; retrievedAt; approval; timeWindow; sampling method; what a count means
- Limitations: A no-result query can mean missing content or content readers cannot find. Low traffic or absent searches do not show low need. Ambiguous analytics are recorded with their meaning, not interpreted.
- If missing: status "not assessed". Request: Export internal search queries (with result counts) for a stated window from the docs search tool, with approval, and say what each count measures.
- Item fields: `query`* (string), `count`* (number), `noResults` (boolean), `clicks` (number), `countMeaning` (string) (* required)

## Release and lifecycle (`release`)

- Assessment: a script gathers and flags; a person or Claude judges
- Input: a signal file named in the profile under `inputs.release`
- Minimum evidence: Release status per feature with public evidence (a release note, a changelog entry on a public release, or a public page). Candidates already carry changelog and planning status.
- Provenance needed: where the status comes from; date
- Limitations: An internal plan or flag is not public availability. A closed ticket is not shipped behavior. A release note that never became a durable guide needs a guide only if readers need one.
- If missing: status "not assessed". Request: List each feature with its status (ga, beta, flagged, planned, deprecated, removed) and a public link or release note date that proves it.
- Item fields: `feature`* (string), `status`* (ga|beta|flagged|planned|deprecated|removed), `publicEvidence` (string), `date` (date), `breaking` (boolean), `defaultChanged` (boolean), `upgradePath` (boolean), `releaseNoteOnly` (boolean), `task` (string) (* required)

## Accuracy and reproducibility (`accuracy`)

- Assessment: needs human or Claude judgment
- Input: a signal file named in the profile under `inputs.accuracy`
- Minimum evidence: Verification results for specific claims, each naming the method: static (read in source), executed (run in a disposable environment), or reported (told by someone). Claims themselves are extracted by script.
- Provenance needed: method; who verified; date; version or environment
- Limitations: Reading code is not testing behavior. A declared option is not proof code reads it. A documented claim is not evidence for itself. Anything with external side effects stays unverified unless run safely.
- If missing: status "not assessed". Request: For each high-risk claim, record how it was verified (static, executed, or reported), by whom, when, and against which version. Do not run commands with external side effects.
- Item fields: `id`* (string), `kind`* (stale-claim|ui-label|example|api-behavior|prerequisite|version|contradiction|procedure), `page`* (string), `claim`* (string), `result`* (confirmed|partial|not-found|overstated|failed|unverified), `method`* (static|executed|reported), `verifiedBy` (string), `date` (date), `productDefect` (boolean), `notes` (string) (* required)

## Operational risk (`risk`)

- Assessment: needs human or Claude judgment
- Input: a signal file named in the profile under `inputs.risk`
- Minimum evidence: Named risks for a task or page: errors, limits, quotas, destructive operations, security, authentication, permissions, privacy, backups, rollback, recovery. The script flags pages that mention risky operations; a person judges whether guidance is adequate.
- Provenance needed: who identified the risk; source
- Limitations: Public documentation must not reveal private implementation details. A risk marked not public-safe may shape a need but its details must not appear in a published brief.
- If missing: status "not assessed". Request: List the destructive, security, limit, and recovery cases for each task, and mark which details are safe to publish.
- Item fields: `id`* (string), `category`* (error|limit|quota|destructive|security|auth|permission|privacy|backup|rollback|recovery), `task` (string), `page` (string), `publicSafe`* (boolean), `note` (string) (* required)

## Integration and workflow completeness (`integration`)

- Assessment: a script gathers and flags; a person or Claude judges
- Input: a signal file named in the profile under `inputs.integration`
- Minimum evidence: For a workflow that spans products or systems, the ordered steps the product actually supports (setup, input, output, callback, error, retry, permission, verification, recovery, production readiness). Steps in the profile are matched to pages by script.
- Provenance needed: source of the workflow description
- Limitations: Feature coverage does not prove end-to-end coverage. Do not require callbacks, retries, or production checklists where the product has none; mark them not applicable.
- If missing: status "not assessed". Request: Describe each multi-system workflow as ordered steps in the profile (task.steps) and mark steps that do not apply.
- Item fields: `workflow`* (string), `step`* (setup|input|output|callback|error|retry|permission|verify|recover|production-readiness), `applies`* (boolean), `task` (string), `note` (string) (* required)

## Accessibility and comprehension (`accessibility`)

- Assessment: a script gathers and flags; a person or Claude judges
- Input: a signal file named in the profile under `inputs.accessibility`
- Minimum evidence: Mechanical checks from the inventory: heading structure, link text, image alternatives, unexpanded acronyms, instructions that rely on a picture or position. Optional manual findings can be supplied.
- Provenance needed: method; who checked
- Limitations: Partial by design. Contrast, keyboard use, focus order, screen readers, rendered output, and localization readiness are not checked mechanically.
- If missing: status "not assessed". Request: Run a full accessibility check (automated and manual) on the pages that matter and record findings with the method and the person who checked.
- Item fields: `page`* (string), `issue`* (string), `method`* (string), `checkedBy`* (string) (* required)

## Governance (`governance`)

- Assessment: a script gathers and flags; a person or Claude judges
- Input: a signal file named in the profile under `inputs.governance`
- Minimum evidence: The inventory shows duplicate titles, shared canonicals, redirects, orphans, and date conflicts. Owners and review dates come from the profile or a supplied list.
- Provenance needed: source of ownership and review data
- Limitations: A current timestamp is not proof of current content. Conflicting sources need a person to pick the authority.
- If missing: status "not assessed". Request: List page owners and last review dates, and any known source-of-truth conflicts, for the pages in this area.
- Item fields: `page`* (string), `owner` (string), `reviewedOn` (date), `status` (current|stale|conflicting|duplicate|orphaned), `note` (string) (* required)
